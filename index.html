MindSpec · 2026 · Applied AI Engineer

Structured evidence extraction from scientific papers

Long neuroscience papers, tables and figures included, turned into records in a 167-field, 9-table evidence schema, validated on the way in. Curation that took a person about three hours per paper now takes about 45 minutes plus a reviewer's sign-off.

Context

MindSpec builds a structured evidence base from the neuroscience literature. Every paper has to be read, its findings pulled out, and each finding placed into a schema so it can be compared with findings from other papers. Doing this by hand is slow and inconsistent, and the schema itself keeps evolving as the science does.

Problem

The first-generation pipeline (case 03) proved the idea but struggled with exactly the things that make scientific papers hard: dense tables and figures that garble when parsed, output that drifts from the schema, and duplicate records creeping in across hundreds of documents.

Approach

  • Structured outputs, not free text. Rebuilt extraction around Claude's structured outputs with Pydantic models as the contract. Every record is validated against the 167-field schema before it's stored; anything that doesn't fit is rejected, not silently coerced.
  • Provenance-aware deduplication. Each record carries where it came from, so the same finding reported in two places is merged rather than double-counted.
  • Automated vocabulary checks. Terms are checked against controlled vocabularies at extraction time instead of at review time.
  • Regression fixtures and observability. A fixed set of gold-standard papers runs on every change, traced in LangSmith, so a prompt or model change that degrades a field shows up before it ships.

Result

Populated the schema across 10+ gold-standard publications with reviewer sign-off. Per-paper curation dropped from about 3 hours of manual work to about 45 minutes plus review. The reviewer stays in the loop by design; the pipeline's job is to make their time count.

MindSpec · 2026 · Applied AI Engineer

Hybrid retrieval with auditing and regression safety

A retrieval layer that combines dense and sparse search over the evidence base, with an LLM-as-judge audit and regression fixtures so that a change to the index or the prompts can't quietly make results worse.

Problem

Scientific vocabulary is exact. A pure embedding search finds things that are semantically close but misses precise terms, identifiers and rare entities; a pure keyword search does the opposite. Neither alone is trustworthy enough to sit under an evidence base, and any retrieval system that isn't measured will degrade the first time someone tunes it.

Approach

  • Dense plus sparse. BGE-M3 embeddings in pgvector with an HNSW index for semantic matches; PostgreSQL full-text search for exact terms. Both run on the same database, so there's one system to operate.
  • Reciprocal Rank Fusion. The two result lists are merged with RRF rather than a tuned weighting, which is robust and has nothing to overfit.
  • LLM-as-judge auditing. A model grades retrieved passages for relevance on a sample, giving a continuous read on quality without a human labelling every query.
  • Regression fixtures. A fixed set of queries with known-good results runs on every change. If a fixture breaks, the change doesn't ship.
  • Observability. Every query is traced in LangSmith, so a bad result can be followed back to the passage, the embedding and the fusion step that produced it.

Result

The retrieval layer that the extraction pipeline and its reviewers depend on, with change safety built in rather than bolted on. Vocabulary checks and provenance-aware deduplication sit in front of it so that what gets retrieved is clean.

MindSpec · 2025–2026 · AI Research Intern

First-generation RAG pipeline and ontology normalization

The version that proved the idea: 50+ biomedical PDFs converted into 4,400 structured records, and an exposure-term normalizer that maps free text to standard ontologies with about 91% resolved automatically.

Problem

Turn a shelf of biomedical PDFs into records a database can hold, complete with the statistical details that make a finding usable: confidence intervals and the covariates each estimate was adjusted for. Then make the exposure terms in those records comparable across papers, when every author names the same thing differently.

Approach

  • Parsing. Docling for document structure, PubMedBERT embeddings for retrieval, pgvector for storage, Claude for extraction.
  • Context limits. Papers that didn't fit in one pass went through a two-pass fallback rather than being truncated.
  • Normalization ladder. Exposure terms tried exact match first, then token match, then RapidFuzz fuzzy match. Each step only ran if the previous one failed.
  • Expert routing. Terms that no step could resolve with confidence went to a reviewer instead of being guessed. Resolved terms were linked to ChEBI, ECTO and ICD-10.

Result

4,400 structured records from 50+ source PDFs, including confidence intervals and adjustment metadata. About 91% of exposure terms canonicalized without human input. The pipeline was later rebuilt (case 01) around what this version taught: where parsing breaks, where schemas drift, and where duplicates come from.

Independent · 2025

An HR assistant that acts, not answers

An MCP server that gives Claude Desktop 13 HR tools. One plain-English instruction onboards a new hire end to end: the record is created, the IT ticket opened, the welcome email sent, the kickoff meeting scheduled.

Problem

Most "AI assistants" for internal processes answer questions about the process. The useful version does the process. Onboarding is a good test: four systems, a fixed order, and a lot of copy-paste between them.

Approach

  • Tools, not prompts. Built an MCP server with FastMCP exposing 13 tools across onboarding, leave, ticketing, meetings and email. Each tool does one thing and reports back what it did.
  • The model plans, the tools act. Claude Desktop reads the instruction, decides which tools to call and in what order, and calls them. The server never guesses intent; it just executes well-defined actions.
  • One prompt, four actions. "Onboard Priya as a data analyst starting Monday" becomes: create employee record, open IT ticket, send welcome email, schedule kickoff.

Result

A working end-to-end agent over a standard protocol, so the same tools work with any MCP-capable client. Code is public.

Independent · 2025

A store assistant that knows when to query and when to read

A chatbot that classifies each question by intent and sends it down the right path: text-to-SQL against a live product database for stock and price questions, retrieval over policy documents for everything about returns and shipping.

Problem

"Do you have this in size 10?" and "What's your return policy?" look alike to a chatbot and are answered from completely different sources. Sending both to a single RAG index gets the first one wrong; sending both to SQL gets the second one wrong.

Approach

  • Intent routing first. Each message is classified before anything else happens: inventory question, policy question, or small talk.
  • Text-to-SQL for facts. Inventory questions are turned into SQL against the product database, so the answer is the current truth, not an embedding's memory of it.
  • RAG for policy. Policy questions retrieve from FAQ documents and answer with the source in hand.
  • A catalog to query. A web-scraping pipeline builds and refreshes the product database the SQL path runs against.

Result

A working assistant on Llama 3.3 via Groq, with the routing logic that stops factual questions being answered from prose. Code is public.

Bear Cognition · 2024 · Data Analyst Intern

Replacing forms with dashboards for an athlete training facility

Nine Plotly Dash applications that replaced manual JotForm workflows for a facility training Olympic and professional athletes, writing directly to Snowflake. They were still in production more than a year after I left.

Problem

Data about athletes was being collected through forms and moved around by hand. It was slow, error-prone, and disconnected from the warehouse where it needed to end up.

Approach

  • Write at the source. Each Dash application captured data and wrote it straight to Snowflake, removing the manual step entirely.
  • Nine apps, not one. Each workflow got its own focused application rather than one sprawling tool, which is why they survived staff turnover and were still in use 12+ months later.
  • A second prototype. In the same internship, built a reusable OCR ingestion and analytics tool for LTL shipping companies: receipts and orders parsed into a Dash AG Grid dashboard backed by MongoDB.

Result

Nine applications in daily use, and the durability that matters most for internal tools: they kept working after the person who built them was gone.

About

I'm an applied AI engineer at MindSpec in McLean, Virginia, working from Clemson, South Carolina. I build the systems that read scientific literature so people don't have to read all of it: LLM extraction against strict schemas, hybrid retrieval, and the evaluation harnesses that make both trustworthy.

I came to this through data. I'm most interested in applied AI and research engineering roles where I can own the whole loop, from raw documents to a result someone will act on.
